# دستیار هوش مصنوعی

- صفحهٔ اصلی: `index.html`
- استایل مشترک: `styles.css`
- رفتارهای تعاملی: `app.js`
- برای صفحه‌های بعدی از `pages/*.html` و لینک‌های نسبی استفاده کنید.
- فایل‌ها در پیش‌نمایش زنده مستقیماً اجرا می‌شوند؛ وابستگی به build یا npm اضافه نکنید.

## بررسی محیط و تصمیم فنی

در بررسی این پروژه فقط این فایل‌ها و قابلیت‌ها وجود دارند: `index.html`، `styles.css` و `app.js`؛ هیچ `package.json`، runtime (Node/Go/Python)، فایل migration، سرویس پایگاه‌داده، API یا test runner در workspace دیده نمی‌شود. اجرای پروژه نیز با بازکردن مستقیم `index.html` انجام می‌شود. بنابراین در این محیط هیچ backend یا database قابل راه‌اندازی وجود ندارد و انتخاب فناوری یا ایجاد اتصال ساختگی، امنیت واقعی ایجاد نمی‌کند.

**نتیجه اجرایی این مرحله:** backend امن، احراز هویت، نشست، RBAC، API چندمستاجری و مهاجرت از `localStorage` در این workspace پیاده‌سازی نشده‌اند؛ چون زیرساخت لازم موجود نیست. داشبورد و مسیرهای فعلی عمداً بازنویسی نشده‌اند.

برای شروع پیاده‌سازی واقعی باید در workspace یک runtime قابل اجرا و پایگاه‌دادهٔ مدیریت‌شده فراهم شود. سپس می‌توان یک API مستقل (مثلاً با runtime مورد تأیید محیط) و PostgreSQL را به‌صورت واقعی مستقر کرد. این انتخاب تا زمان تأیید runtime، نسخه پایگاه‌داده، روش secret management، شبکه و محیط staging قطعی اعلام نمی‌شود.

## وضعیت جداسازی داده
این workspace فقط یک frontend استاتیک (`index.html`، `styles.css` و `app.js`) است و هیچ runtime بک‌اند، API احراز هویت، پایگاه‌داده، مدیریت نشست یا لایهٔ دسترسی سمت سرور در اختیار پروژه نیست. بنابراین نقش‌های مالک، مدیر و کاربر را نمی‌توان به‌صورت واقعی و امن در همین workspace پیاده‌سازی کرد؛ افزودن شرط نقش در JavaScript یا `localStorage` کنترل دسترسی سمت سرور محسوب نمی‌شود و قابل دور زدن است.

## مسیر لازم برای راه‌اندازی واقعی

پس از فعال‌شدن backend و database، این ترتیب باید اجرا و با شواهد ثبت شود:

1. ایجاد migration برای `businesses`، `users`، عضویت‌ها، `sessions` و `customers` با کلیدهای خارجی و index روی `business_id`.
2. ثبت‌نام و ورود با hash امن رمز، نشست تصادفی در cookieهای `HttpOnly`/`Secure`/`SameSite`، انقضا، خروج و ابطال نشست؛ هیچ token یا secret حساسی در JavaScript مرورگر قرار نگیرد.
3. استخراج `user_id` و عضویت/نقش از نشست در سرور؛ هرگز اعتماد به `business_id` یا `role` ارسالی کلاینت نشود.
4. اعمال middleware احراز هویت، tenant scope و مجوز نقش روی **تمام** endpointهای خواندن، افزودن، ویرایش و حذف؛ پاسخ‌های `401` و `403` تفکیک شوند.
5. ایجاد endpointهای مشتریان و تنظیمات کسب‌وکار با validation سروری، محدودیت نرخ، audit log و queryهایی که tenant را از نشست به‌صورت اجباری اعمال می‌کنند.
6. مهاجرت دادهٔ قبلی فقط پس از ورود کاربر و تأیید کسب‌وکار مقصد انجام شود؛ دادهٔ `localStorage` بدون mapping مالکیت به‌طور خودکار وارد نشود و قبل از حذف، export/backup و گزارش نتیجه ارائه شود.
7. اجرای تست‌های integration با دو کسب‌وکار A/B و سه نقش، شامل تلاش برای ارسال شناسه کسب‌وکار دیگر، CRUD، نشست منقضی و دسترسی مستقیم به شناسه منابع؛ تا سبز نشدن این تست‌ها قابلیت آماده اعلام نشود.

## شواهد فعلی

هیچ endpoint، migration، نشست سروری یا تست جداسازی API در این workspace وجود ندارد؛ بنابراین نتیجهٔ تست واقعی دو کسب‌وکار **اجرا نشده** است، نه موفق. برای فعال‌سازی ادامه کار، backend/database و روش استقرار باید در workspace فراهم یا به پروژه متصل شود.

پیاده‌سازی نشده و عمداً اتصال ساختگی اضافه نشده است. برای اجرای واقعی، زیرساخت باید این اجزا را فراهم کند:

- API قابل اجرا با ثبت‌نام، ورود، خروج و نشست امن (ترجیحاً cookie `HttpOnly`، `Secure` و `SameSite` به‌همراه انقضا و ابطال نشست)
- پایگاه‌دادهٔ واقعی با جداول `users`، `businesses`، عضویت کاربر در کسب‌وکار و نشست‌ها
 - نقش‌های `owner`، `admin`، `marketer` و `customer` باید از عضویت و نشست معتبر سمت سرور تعیین شوند؛ نقش ارسالی از مرورگر قابل اعتماد نیست
- مجوزهای صریح برای هر endpoint و هر عملیات: مالک مدیریت اعضا و تنظیمات، مدیر مدیریت داده‌های کسب‌وکار، و کاربر فقط دسترسی‌های عملیاتی تعریف‌شده
- اعمال فیلتر `business_id` از نشست روی تمام queryهای خواندن، افزودن، ویرایش و حذف؛ هرگز اعتماد به `business_id` ارسالی کلاینت
- اعتبارسنجی ورودی، پاسخ‌های استاندارد `401` برای نشست نامعتبر و `403` برای نقش غیرمجاز، و ثبت رویدادهای حساس

## آزمون‌های لازم (در این workspace اجرا نشده‌اند)
آزمون API بین دو کسب‌وکار، احراز هویت، نشست منقضی‌شده، ماتریس نقش‌ها و CRUD مجاز/غیرمجاز اجرا نشده‌اند؛ چون API و پایگاه‌داده‌ای برای اجرا وجود ندارد. بنابراین نتیجهٔ موفق برای جداسازی tenant یا RBAC اعلام نمی‌شود.

## وضعیت فعلی داده‌ها
برای جلوگیری از اشتباه، داده‌های آزمایشی `localStorage` با کلید `hoshyar:<business-id>:...` نام‌گذاری می‌شوند و از دادهٔ کسب‌وکار دیگر خوانده نمی‌شوند؛ این فقط مرزبندی مرورگری قابل دور زدن است و امنیت محسوب نمی‌شود. آزمون محدود فعلی را در Console مرورگر اجرا کنید:
```js
hoshyarSecurity.runTenantIsolationSmokeTest()
```
`true` فقط جداسازی کلیدهای مرورگر را نشان می‌دهد، نه کنترل دسترسی سمت سرور.

برای تکمیل این درخواست باید ابتدا قابلیت Backend/Database در workspace فعال شود یا یک سرویس بک‌اند واقعی و قابل استقرار به پروژه متصل شود؛ پس از آن می‌توان endpointها، مهاجرت داده و تست جداسازی دو کسب‌وکار را واقعاً پیاده‌سازی و اجرا کرد.

## بررسی فناوری‌های اتصال و یکپارچه‌سازی (وضعیت: آماده‌سازی نشده)

این فهرست **بررسی معماری و معیار انتخاب** است، نه اعلام اتصال یا تأیید قابلیت سرویس‌ها. در این workspace هیچ حساب، کلید API، قرارداد تجاری، شماره تلفن، درگاه، پرینتر یا سرویس بیرونی متصل و آزمایش نشده است. قبل از خرید یا پیاده‌سازی باید مستندات فعلی، دسترس‌پذیری برای کشور/حساب کسب‌وکار، قیمت، SLA، محدودیت قانونی و محیط sandbox هر گزینه جداگانه تأیید شود.

### معماری پیشنهادیِ قابل کنترل

- تمام کلیدها و credentialها فقط در backend نگهداری شوند؛ frontend استاتیک هرگز مستقیماً به تلفن، پرداخت یا سرویس دارای کلید متصل نشود.
- برای تماس، پیامک، TTS و چاپ از صف job، شناسهٔ idempotency، retry با backoff، dead-letter و ثبت رویداد استفاده شود.
- ورودی صوت و متن قبل از ارسال به مدل کمینه‌سازی و رمزنگاری شود؛ retention، رضایت، حذف و دسترسی tenant در backend اعمال شود.
- پرداخت فقط با چرخهٔ `create → callback → server-side verify → fulfill` انجام شود و مبلغ/سفارش از پایگاه‌دادهٔ سمت سرور خوانده شود.
- برای هر اتصال adapter جدا، timeout، circuit breaker، health check و feature flag در نظر گرفته شود تا قطعی یک سرویس کل محصول را متوقف نکند.

### دروازهٔ تأیید قبل از اعلام «آماده»

برای هر سرویس باید این شواهد ثبت شود: مستندات نسخه‌دار و شرایط استفاده، قرارداد/مجوز، credentials محیط آزمایشی، تست موفق و خطا، latency و هزینهٔ اندازه‌گیری‌شده، لاگ بدون افشای دادهٔ حساس، و برنامهٔ fallback. تا وقتی این شواهد در backend موجود و تست نشده‌اند، وضعیت همهٔ موارد بالا **اتصال‌نشده و تأییدنشده** است.

**جمع‌بندی رابط:** برای چند فرایند، فرم و مدیریت محلی واقعیِ مرورگر وجود دارد؛ بخشی از صفحه‌های اصلی نیز عمداً وضعیت اتصال‌نشده/نمونه را نشان می‌دهند. این‌ها با پنل چندمستاجری عملیاتی، ثبت رویداد قابل‌اعتماد یا محصول آمادهٔ انتشار برابر نیستند. در این مرحله کمبود رابطی که بدون بک‌اند باید با دادهٔ ساختگی پر شود وجود نداشت؛ بنابراین برای حفظ رفتار و داده‌های فعلی، رابط بازنویسی نشد.

## معماری پیشنهادی بک‌اند و مدل داده

این طرح پیشنهادی است، نه پیاده‌سازی یا انتخاب قطعی فناوری. چون workspace فعلی فقط سایت استاتیک دارد و runtime، پایگاه‌داده، سامانهٔ استقرار بک‌اند یا قرارداد سرویس در آن دیده نمی‌شود، API و migration در این مرحله ساخته یا آزمایش نشده‌اند. پس از فعال‌شدن backend در workspace، یک API نسخه‌دار و پایگاه‌دادهٔ رابطه‌ای مدیریت‌شده (مانند PostgreSQL) مناسب است؛ کلیدها، تراکنش‌ها و قوانین دسترسی باید فقط در سرور باشند.

### موجودیت‌ها و روابط پایه

همهٔ داده‌های کسب‌وکاری باید به `business_id` متصل شوند و جداسازی tenant از نشست معتبر سرور استخراج شود، نه از شناسهٔ ارسالی مرورگر.

- `businesses` ← ریشهٔ tenant و تنظیمات کسب‌وکار.
- `users` ← هویت و اطلاعات ورود؛ رمز فقط به‌شکل hash امن ذخیره شود.
- `business_memberships` ← رابطهٔ چندبه‌چند کاربر و کسب‌وکار، وضعیت عضویت و نقش (`owner`، `manager`، `marketer`، `customer` یا نقش‌های موردتأیید مالک). قید یکتای عضویت برای `(business_id,user_id)`.
- `registration_requests` / `invitations` ← درخواست ثبت‌نام، تصمیم مالک، زمان و عامل تصمیم؛ ایجاد عضویت فقط پس از سیاست تأیید مشخص.
- `customers` و `customer_interactions` و `followups` ← پروندهٔ CRM و سوابق وابسته؛ دسترسی و retention مشخص.
- `catalog_items` ← خدمت/محصول، قیمت و مدت؛ قیمت سفارش باید snapshot شود تا ویرایش کاتالوگ تاریخچه را تغییر ندهد.
- `orders` و `order_items` ← سفارش، وضعیت کاری و جزئیات اقلام؛ مستقل از وضعیت پرداخت.
- `appointments` ← مشتری/اطلاعات تماس، خدمت، بازهٔ زمانی و وضعیت؛ قید هم‌زمانی/رزرو باید در تراکنش پایگاه‌داده اعمال شود.
- `calls` ← شناسهٔ سرویس‌دهنده، وضعیت اعتبارسنجی، زمان و متادیتای کمینه؛ فایل ضبط/متن مکالمه با سیاست جداگانهٔ رضایت و نگهداری.
- `support_tickets` و `support_messages` ← تیکت، کانال و پیام؛ هویت نویسنده و tenant در سرور تعیین شوند.
- `plans` و `subscriptions` ← کاتالوگ پلن و عضویت کاربر؛ اشتراک به پرداخت موفق صرفاً از مسیر سروری مرتبط شود.
- `payments` و `payment_events` ← مبلغ/واحد پول، ارائه‌دهنده، شناسهٔ یکتا، وضعیت و callback؛ رویداد webhook قابل تکرار باید idempotent باشد.
- `cost_entries` و `usage_records` ← مصرف/هزینه با منبع، دوره، واحد و وضعیت اعتبارسنجی؛ هزینهٔ دستی/تخمینی با دادهٔ تأییدشده ادغام نشود.
- `marketer_prospects` و `trial_quota_ledger` ← سرنخ‌های منتسب به بازاریاب و دفترکل مصرف تغییرناپذیر؛ سهمیه برای هر سرنخ جدا و به‌صورت اتمیک کنترل شود.
- `professional_package_definitions` و `professional_package_orders` ← قیمت و تعریف تأییدشده با نسخه‌بندی/snapshot؛ بسته از پلن اشتراک، پرداخت و تماس جدا بماند. تأیید تعریف فقط پس از تصمیم صریح مالک ثبت شود.
- `notifications` و `audit_events` ← اعلان قابل‌مشاهده و audit تغییرناپذیر؛ نوع، زمان، نتیجه، عامل و شناسهٔ مرتبط، بدون کپی اطلاعات حساس غیرضروری.
- `integration_accounts` / ارجاع به secret manager ← فقط شناسه و وضعیت اتصال؛ secret واقعی در مخزن اسرار خارج از دیتابیس عمومی و فرانت‌اند.

برای همهٔ رکوردها شناسهٔ غیرقابل حدس، `created_at`/`updated_at`، قیدهای خارجی، index روی tenant و زمان، و قواعد حذف/آرشیو تعریف شود. حذف حساب نباید سوابق پرداخت یا audit را بی‌قاعده پاک کند؛ retention و درخواست حذف باید مطابق سیاست مالک و الزامات قانونی باشد.

### قرارداد API پیشنهادی

قرارداد زیر فقط جهت آماده‌سازی است؛ endpointها اکنون وجود ندارند. همهٔ مسیرها زیر `/api/v1`، با JSON، اعتبارسنجی schema در سرور، خطاهای استاندارد و شناسهٔ درخواست باشند.

| مسیر نمونه | هدف و کنترل الزامی |
|---|---|
| `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/session` | درخواست حساب، ورود و ابطال نشست؛ cookie امن `HttpOnly`, `Secure`, `SameSite`، CSRF مناسب و محدودیت نرخ |
| `GET /admin/registration-requests`, `POST /admin/registration-requests/{id}/decision` | فقط مالک مجاز به بررسی درخواست؛ ثبت عامل و زمان تصمیم در audit |
| `GET/POST /businesses/{id}/customers`, `PATCH/DELETE /customers/{id}` | CRM؛ tenant از نشست و مالکیت منبع در هر درخواست بررسی شود |
| `GET/POST /orders`, `PATCH /orders/{id}` و `GET/POST /appointments` | عملیات کسب‌وکار؛ اعتبارسنجی وضعیت و رزرو اتمیک؛ سفارش و پرداخت دو چرخهٔ مستقل |
| `GET /calls`, `POST /provider-webhooks/calls` | webhook فقط با امضا/اعتبارسنجی ارائه‌دهنده؛ دادهٔ دریافتی تا اعتبارسنجی «تأییدنشده» بماند |
| `GET/POST /support/tickets`, `POST /support/tickets/{id}/messages` | کنترل عضویت و نویسنده؛ پاسخ اپراتور فقط از نشست دارای نقش پشتیبان/مدیر |
| `GET/POST /plans`, `POST /subscriptions` | مجوز مالک برای تعرفه/تخصیص؛ ایجاد اشتراک فعال فقط پس از سیاست پرداخت سمت سرور |
| `POST /payments/checkout`, `POST /webhooks/payments/{provider}` | مبلغ از رکورد سمت سرور؛ callback به‌تنهایی پرداخت نیست؛ verify سمت سرور و کلید یکتای تراکنش پیش‌شرط fulfillment است |
| `GET/POST /usage`, `POST /marketer/prospects/{id}/trial-uses` | نقش، انتساب بازاریاب، سهمیه و مصرف در یک تراکنش/قفل اتمیک؛ رد پس از اتمام سهمیه بدون اعتماد به مرورگر |
| `GET /notifications`, `PATCH /notifications/{id}`, `GET /audit-events` | tenant و مجوز؛ audit فقط افزایشی، بدون endpoint ویرایش/حذف برای کاربر عادی |
| `GET /integrations/health`, `POST /integrations/{provider}/connect` | سلامت و چرخهٔ اتصال مدیریت‌شده؛ اسرار هرگز به مرورگر بازگردانده نشوند |

پاسخ‌ها باید حداقل خطاهای `401` (نشست نامعتبر)، `403` (مجوز ناکافی)، `404` (منبع خارج از دامنه/ناموجود)، `409` (تعارض/idempotency) و `422` (اعتبارسنجی) را تفکیک کنند. برای ساخت رکورد و webhook از `Idempotency-Key` یا شناسهٔ رویداد ارائه‌دهنده استفاده شود تا retry و تازه‌سازی باعث تکرار سفارش، پرداخت، سهمیه یا اعلان نشود.

## الزامات امنیتی و اتصال‌های واقعی

- **هویت و نقش:** گذرواژهٔ hash‌شده، نشست کوتاه‌عمر/قابل ابطال، MFA برای مالک/مدیر در صورت امکان، تأیید مالک از نشست احراز‌شده، RBAC سمت سرور و حداقل‌سازی مجوز.
- **چندمستاجری:** tenant از عضویت نشست تعیین شود؛ تمام queryهای خواندن/نوشتن و جست‌وجو به tenant محدود شوند؛ دسترسی مستقیم با شناسهٔ رکورد نیز کنترل شود. تست‌های منفی بین دو کسب‌وکار الزامی‌اند.
- **اطلاعات حساس:** رمزنگاری انتقال و ذخیره، عدم ثبت شماره/پیام/secret در لاگ، دسترسی محدود به دادهٔ مالی و متن تماس، دورهٔ نگهداری و حذف، رضایت ضبط/پردازش و ثبت audit دسترسی‌های حساس.
- **سهمیهٔ دمو:** دفترکل سمت سرور، تراکنش اتمیک و کلید idempotency برای هر اقدام؛ محدودیت مرورگر صرفاً تجربهٔ رابط است و در برابر دستکاری قابل اتکا نیست.
- **audit:** ثبت append-only در سرور، عامل احراز‌شده، زمان سرور، نوع، نتیجه، شناسهٔ منبع و correlation ID؛ حفاظت/پشتیبان‌گیری و دسترسی خواندن محدود. `localStorage` گزارش امنیتی نیست.
- **هوش مصنوعی:** backend proxy با secrets سمت سرور، allowlist ابزارها، محدودیت نرخ/هزینه، کمینه‌سازی و حذف دادهٔ شخصی، کنترل خروجی و ثبت نسخه/مدل؛ مدل حق اجرای پرداخت/تغییر نقش/عملیات برگشت‌ناپذیر بدون مجوز و تأیید سرور نداشته باشد.
- **تلفن:** ارائه‌دهندهٔ پشتیبانی‌شده برای کشور هدف، شماره/اتصال و webhook امضاشده؛ نگاشت شناسهٔ تماس، وضعیت و مدت پس از اعتبارسنجی، رضایت و سیاست ضبط. تا آن زمان تماس واقعی یا مصرف تلفنی نباید اعلام شود.
- **پرداخت:** پذیرنده و sandbox تأییدشده، ساخت checkout در سرور، callback امضاشده و verify مستقل، idempotency و تطبیق مبلغ/ارز/سفارش؛ فقط بعد از verify وضعیت پرداخت موفق و تحویل قابل ثبت است.

هیچ کلید AI، رمز درگاه، token تلفن، secret webhook یا credential سرور نباید در HTML/JS/CSS، `localStorage` یا repository قرار گیرد. استفاده از secret manager و چرخش کلیدها لازم است.

## مهاجرت داده و تصمیم‌های لازم

داده‌های فعلی در کلیدهای `hoshyar:<business-id>:...` مرورگر هستند و احراز مالکیت، صحت و انحصار ندارند. آن‌ها نباید خودکار به tenant سرور نسبت داده شوند. در صورت درخواست مهاجرت، ابتدا export محلی، نمایش پیش‌نمایش، تأیید هویت و نگاشت صریح کسب‌وکار، اعتبارسنجی، گزارش رکوردهای ردشده و امکان backup لازم است؛ اطلاعات تماس و پیام به‌صورت پیش‌فرض به سرور منتقل نشوند.

تصمیم‌های لازم از مالک/تیم پیش از پیاده‌سازی: (۱) runtime و میزبان backend و پایگاه‌دادهٔ تأییدشده، محیط staging و secret management؛ (۲) ماتریس دقیق مجوز هر نقش و فرایند ثبت‌نام/تأیید مالک؛ (۳) معنای دقیق «مورد»، خروجی، معیار پذیرش، زمان تحویل و سیاست لغو/بازپرداخت بسته‌های بازاریابی؛ (۴) کشور و ارائه‌دهندگان مجاز تلفن، AI و پرداخت و شرایط قانونی/حریم خصوصی؛ (۵) سیاست نگهداری، رضایت و حذف تماس/CRM/پشتیبانی؛ (۶) روش و دامنهٔ مهاجرت داده‌های مرورگر.

## مراحل باقی‌مانده پس از این مرحله

**۴ مرحلهٔ اجرایی پیشنهادی باقی می‌ماند** (برآورد نقشهٔ راه، نه کار انجام‌شده):

1. فعال‌سازی backend/database در workspace و تأیید تصمیم‌های مالک، محیط‌ها، مدل مجوز و سیاست داده.
2. پیاده‌سازی schema/migration، احراز هویت و نشست، tenant isolation، RBAC و تست‌های امنیتی دو کسب‌وکار.
3. انتقال تدریجی قابلیت‌های دامنه و APIها (CRM، سفارش/نوبت، تماس/پشتیبانی، اشتراک/هزینه، سهمیه، اعلان/audit و مهاجرت اختیاری داده) با تست‌های integration.
4. اتصال AI، تلفن و پرداخت در sandbox و سپس staging، تست خطا/retry/rollback و حریم خصوصی؛ انتشار فقط پس از شواهد اجرایی، مانیتورینگ و تأیید مالک.

این مرحله فقط ممیزی کد و مستندسازی معماری را انجام می‌دهد. API، پایگاه‌داده، اتصال واقعی، مهاجرت داده و آزمون عملی مرورگر/سرور در آن اجرا نشده‌اند؛ بنابراین این پروژه را امن، متصل یا آمادهٔ انتشار معرفی نمی‌کند.

## مرحلهٔ اجرایی اول: شواهد محیط و طرح انتقال به بک‌اند

### آنچه واقعاً در workspace بررسی شد

فهرست فایل‌های قابل‌ویرایش workspace شامل `README.md`، `index.html`، `styles.css` و `app.js` است. هیچ فایل پیکربندی یا manifest وابستگی مانند `package.json`، `go.mod`، `pyproject.toml`، `requirements.txt`، `Dockerfile`، فایل Compose، migration، تنظیمات CI، یا پیکربندی پایگاه‌داده در فهرست نیست. README نیز صریحاً می‌گوید پیش‌نمایش فایل‌ها را مستقیم اجرا می‌کند و build/npm برای نسخهٔ فعلی در نظر گرفته نشده است.

بنابراین شواهد موجود فقط اجرای فرانت‌اند استاتیک را پشتیبانی می‌کند؛ وجود runtime قابل اجرا برای سرور، پایگاه‌داده، API، ابزار نصب وابستگی یا test runner در این workspace اثبات نشده است. این نتیجه دربارهٔ فایل‌ها و قابلیت‌های قابل مشاهدهٔ همین workspace است، نه ادعایی دربارهٔ همهٔ سرویس‌های حساب کاربری یا زیرساخت خارج از آن. اجرای backend در وضعیت کنونی **ممکن/قابل تأیید نیست** و در این مرحله backend نمایشی یا اتصال ساختگی ساخته نمی‌شود.

### پیشنهاد فنی مشروط

معماری پیشنهادی، مستقل‌کردن API از سایت استاتیک و استفاده از **PostgreSQL** برای داده‌های رابطه‌ای است. برای پیاده‌سازی API، پیشنهاد پایه یک سرویس **Node.js روی نسخهٔ LTS با TypeScript** است: کتابخانه‌ها و ابزارهای بالغ برای API، validation و اتصال سرویس‌ها دارد و برای تیمی که هنوز runtime عملیاتی انتخاب نکرده، گزینهٔ قابل‌دسترسی است. این runtime در workspace فعلی موجود یا تأییدشده نیست؛ پس این پیشنهاد به معنی امکان اجرای Node در همین محیط، یا انتخاب نهایی نیست. اگر runtime دیگری از سوی تیم میزبانی استاندارد شده باشد، باید بر مبنای پشتیبانی، به‌روزرسانی امنیتی، توان عملیاتی و مهارت تیم انتخاب و مستند شود.

PostgreSQL به‌دلیل تراکنش، کلید خارجی، قیدهای یکتا، قفل/کنترل هم‌زمانی و پشتیبانی مناسب از داده‌های مرتبط، برای سفارش، پرداخت، سهمیه و جداسازی کسب‌وکارها مناسب است. پایگاه‌دادهٔ مدیریت‌شده بار patch و نگهداری موتور را کمتر می‌کند ولی به ارائه‌دهنده، محل داده، دسترسی شبکه و هزینه وابسته است؛ self-host روی VPS کنترل بیشتری می‌دهد اما نصب، hardening، ارتقا، پایش، بازیابی و on-call را بر عهدهٔ تیم می‌گذارد. انتخاب نسخه، ارائه‌دهنده، محل میزبانی، SLA و هزینه تا بررسی و تأیید مالک باز است. هیچ سرویس خریداری یا متصل نشده است.

### میزبانی، دامنه و شبکهٔ ایران: تصمیم‌های مالک

پیش از استقرار باید مخاطب‌ها و محل دسترسی‌شان (داخل ایران، خارج ایران یا هر دو)، محل و حساسیت داده، الزامات قانونی/قراردادی و ارائه‌دهندگان مجاز تعیین شود. سپس مالک باید بین میزبانی داخل کشور یا خارج از کشور تصمیم بگیرد؛ دسترس‌پذیری واقعی سرویس‌های AI، تلفن، پیامک، ایمیل و پرداخت از محل منتخب، محدودیت‌های شبکه/تحریم، تأخیر، مسیر callbackهای ورودی و خروجی و امکان دریافت پشتیبانی باید برای هر سرویس جداگانه با آزمون و قرارداد تأیید شود. از روی این workspace نمی‌توان دسترس‌پذیری یا سازگاری هیچ ارائه‌دهنده‌ای را تضمین کرد.

برای دامنه، مالک باید نام و مالک ثبتی را تعیین کند، DNS و تمدید را مدیریت کند و TLS معتبر را برای سایت، API و webhookها فراهم کند. برای عملیات، backup رمزگذاری‌شده و جدا از میزبان اصلی، نگهداری نسخه‌های روزانه/دوره‌ای متناسب با حجم تغییر، محدودکردن دسترسی و رمزگذاری کلیدها لازم است. برنامه باید RPO/RTO مورد قبول، مدت نگهداری، محل نسخه‌ها و مسئول بازیابی را تعیین کند و بازیابی واقعی نسخهٔ پشتیبان به‌صورت دوره‌ای آزمایش شود؛ داشتن فایل backup به‌تنهایی اثبات قابلیت بازیابی نیست. هیچ خرید، ثبت دامنه یا تغییر شبکه در این مرحله انجام نشده است.

| مدیر | عملیات روزمرهٔ کسب‌وکار: مشتریان، سفارش‌ها، نوبت‌ها و پاسخ‌گویی تیکت‌ها؛ گزارش‌های لازم برای کار | به‌طور پیش‌فرض حق تغییر مالک، تأیید نهایی مالک، مشاهده/ویرایش credential، تأیید پرداخت، تغییر قیمت یا تعریف بسته ندارد؛ مالک می‌تواند دامنهٔ دقیق را تصویب کند. |

### مدل دادهٔ رابطه‌ای و قرارداد اولیهٔ API

موجودیت‌های تفصیلی و اتصال‌هایشان در بخش «معماری پیشنهادی بک‌اند و مدل داده» بالا آمده‌اند؛ اینجا قرارداد پایه برای پیاده‌سازی مرحله‌ای تثبیت می‌شود. جدول‌های tenant-scoped باید `business_id` و کلید خارجی داشته باشند و queryها آن را از نشست تعیین کنند. برای نقش‌های چندکسب‌وکاری از `business_memberships` استفاده شود. مبلغ/تعریف بسته و اقلام سفارش snapshot شوند؛ وضعیت سفارش کاری، وضعیت پرداخت و وضعیت تحویل سه مفهوم مستقل بمانند. سهمیهٔ دمو با دفترکل مصرف سروری و تراکنش اتمیک نگهداری شود. اطلاعات حساس تماس و پرداخت تا حد نیاز کمینه شوند.

پیشوند قرارداد `/api/v1`، JSON، شناسهٔ درخواست و validation سمت سرور:

| دامنه | قرارداد اولیه | نکتهٔ امنیتی/رفتاری |
|---|---|---|
| هویت و عضویت | `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/session`; `GET /me/businesses` | نشست cookie امن؛ ثبت‌نام به‌تنهایی عضویت تأییدشده نمی‌سازد. |
| درخواست عضویت | `GET /owner/registration-requests`; `POST /owner/registration-requests/{id}/decision` | فقط مالک مجاز؛ تصمیم، عامل و زمان ثبت audit شوند. |
| مشتری و CRM | `GET/POST /customers`; `GET/PATCH/DELETE /customers/{id}` | scope و مالکیت هر رکورد سمت سرور کنترل شود؛ تعامل‌ها/پیگیری‌ها نیز tenant-scoped باشند. |
| سفارش و نوبت | `GET/POST /orders`; `GET/PATCH /orders/{id}`; `GET/POST /appointments`; `PATCH /appointments/{id}` | کنترل وضعیت و تداخل نوبت در تراکنش؛ ثبت سفارش معادل پرداخت نیست. |
| تماس و پشتیبانی | `GET /calls`; `POST /provider-webhooks/calls`; `GET/POST /support/tickets`; `POST /support/tickets/{id}/messages` | webhook امضاشده و قابل تکرار؛ نویسنده و tenant از نشست/اعتبارسنجی provider، نه از body. |
| اشتراک، پرداخت و هزینه | `GET /plans`; `GET/POST /subscriptions`; `POST /payments/checkout`; `POST /webhooks/payments/{provider}`; `GET /costs` | checkout و verify فقط سمت سرور؛ webhook تکراری idempotent؛ payment success فقط پس از verify. |
| دمو و بستهٔ حرفه‌ای | `GET/POST /marketer/prospects`; `POST /marketer/prospects/{id}/trial-uses`; `GET /professional-packages`; `POST /professional-package-orders` | سهمیه برای بازاریاب/سرنخ مجاز و در تراکنش کنترل شود؛ تعریف بسته تا تأیید مالک نامعین بماند؛ سفارش بسته پرداخت یا تحویل نیست. |
| اعلان و ممیزی | `GET /notifications`; `PATCH /notifications/{id}`; `GET /audit-events` | tenant و مجوز اعمال شود؛ audit افزایشی/غیرقابل ویرایش برای نقش‌های عادی باشد. |

در همهٔ مسیرها پاسخ‌های `401` (نشست نامعتبر)، `403` (مجاز نیست)، `404` (منبع ناموجود یا خارج از دسترس)، `409` (تعارض/تکرار) و `422` (ورودی نامعتبر) تعریف شوند. برای عملیات حساس و webhookها idempotency key یا شناسهٔ یکتای رویداد لازم است. این‌ها قرارداد پیشنهادی‌اند و هیچ endpointای در حال حاضر اجرا نمی‌شود.

### مهاجرت ایمن و تدریجی `localStorage`

1. تا زمانی که هویت و کسب‌وکار مقصد سمت سرور تأیید نشده، import خودکار و اتصال داده‌های محلی به حساب تازه ممنوع باشد.
2. قابلیت export نسخهٔ خام/قابل‌بازیابی محلی، همراه زمان و نسخهٔ schema، پیش از هر انتقال در نظر گرفته شود؛ دادهٔ مبدأ حذف یا بازنویسی نشود.
3. پس از ورود، کاربر کسب‌وکار مقصد را صریحاً انتخاب و preview رکوردها، تعداد، نوع داده، تعارض‌ها و فیلدهای حذف‌شونده را تأیید کند. مقادیر محلی «ادعای کاربر» هستند، نه رویداد/پرداخت/هویت معتبر سرور.
4. import ابتدا به staging/quarantine وارد شود؛ schema validation، mapping شناسه‌ها، duplicate detection و گزارش ردیف‌های پذیرفته/ردشده اجرا شود. پرداخت، هزینهٔ واقعی، تماس تأییدشده، رویداد ممیزی و مصرف سهمیه از دادهٔ مرورگر به‌عنوان حقیقت عملیاتی پذیرفته نشوند.
5. کاربر نتیجه را بازبینی کند؛ commit نهایی با idempotency و audit انجام شود. در صورت خطا rollback تراکنش یا پاک‌سازی صرفاً در staging انجام شود. حذف localStorage فقط با درخواست صریح پس از export و تأیید نتیجه مجاز است.
6. انتقال محدود و قابل تکرار بر اساس نوع داده و tenant انجام شود؛ ابتدا داده‌های کم‌خطر و سپس موارد دارای اطلاعات شخصی با رضایت، مبنای حقوقی و سیاست نگهداری مصوب.

### تصمیم‌های باز و موانع مرحلهٔ بعد

مالک/تیم باید runtime و محیط استقرار backend، ارائه‌دهنده و محل PostgreSQL، روش secret management، محیط staging، ماتریس نهایی نقش‌ها، سیاست تأیید عضو، دورهٔ نگهداری/رضایت، RPO/RTO و محل میزبانی را تأیید کند. تعریف «مورد» و خروجی بستهٔ بازاریابی نیز همچنان تصمیم مالک است. برای اتصال‌های AI، تماس، پیامک و پرداخت باید ارائه‌دهنده و دسترسی مجاز در بازار هدف، قرارداد و محیط sandbox جداگانه انتخاب و آزمون شوند.

**مراحل باقی‌مانده: ۴ مرحلهٔ اجرایی** — (۱) فعال‌کردن و تأیید runtime/backend، پایگاه‌داده و تصمیم‌های محصول/میزبانی؛ (۲) schema و migration، auth/session، tenant isolation و RBAC با تست امنیتی؛ (۳) API دامنه‌ها و مهاجرت اختیاری، با تست‌های integration؛ (۴) اتصال‌های AI/تلفن/پرداخت در sandbox، آزمون staging، بازیابی backup و تأیید عملیاتی. این تعداد نقشهٔ راه است، نه ادعای انجام آن مراحل.

مرحلهٔ سوم در این workspace **مستندسازی شده، اما عملیاتی نشده است**. فایل‌ها و مستندات مراحل قبل بررسی شدند؛ فهرست کلیدهای `localStorage` و شکل‌های مورد استفاده در کد `app.js` نیز برای طرح مهاجرت ثبت شد. چون محتوای واقعی مرورگر در workspace در دسترس نیست، این فهرست، inventory کد است نه تأیید داده‌های موجود در دستگاه کاربر.

## Go API

- Source: `backend/main.go`; module: `backend/go.mod`.
- Endpoints in the project preview use `/api/...` and run in an isolated container.
- Keep the server on `127.0.0.1:8080` and use Go standard-library packages.
- Frontend requests should use `window.MONETIZEAI_API_BASE` in the platform preview, with `/api/` as the self-hosting fallback.
- `backend/monetize_runtime.go` provides persistent JSON storage, secure password hashing, uploads and allowlisted external API requests.
