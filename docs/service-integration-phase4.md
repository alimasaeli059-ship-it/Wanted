# مرحلهٔ اجرایی چهارم: اتصال سرویس‌ها و آزمون نهایی مرحله‌ای

> **وضعیت در این workspace: برنامهٔ اجرایی مستند شده؛ هیچ سرویس یا بک‌اندی متصل، پیاده‌سازی یا در محیط واقعی آزمایش نشده است.** در فهرست فایل‌های قابل مشاهده، فقط فرانت‌اند استاتیک و اسناد پروژه وجود دارد؛ runtime بک‌اند، API، PostgreSQL، تنظیمات staging، secret manager یا test runner دیده نمی‌شود. داشتن مستندات معماری، حساب احتمالی بیرون از workspace یا نام یک ارائه‌دهنده به‌تنهایی وجود سرویس عملیاتی را ثابت نمی‌کند. دسترسی به زیرساخت‌های بیرون از فایل‌های قابل مشاهده از این workspace قابل تأیید نیست.

## ۱. نتیجهٔ بررسی و دامنهٔ کار انجام‌شده

بررسی هدفمند این مرحله به `README.md`، `docs/security-auth-phase2.md`، `docs/api-data-migration-phase3.md` و فهرست فایل‌های workspace محدود شد. فایل‌های پیکربندی مرتبطی مانند manifest وابستگی، Docker/Compose، تنظیمات استقرار/CI، schema یا migration، API server و تست در فهرست وجود ندارند. README اجرای مستقیم فرانت‌اند استاتیک را توصیف می‌کند. هیچ نشانهٔ قابل‌راستی‌آزمایی از backend قابل اجرا، PostgreSQL، محیط staging، مدیریت امن secret یا اعتبارنامهٔ سرویس‌دهنده در فایل‌های پروژه وجود ندارد.

این نتیجه فقط دربارهٔ امکانات قابل مشاهده و قابل اثبات در این workspace است؛ دربارهٔ سرویس یا حسابی خارج از آن ادعای نبود قطعی نمی‌کند. اما تا وقتی تیم میزبان و مالک دسترسی و شواهد محیط را فراهم نکنند، اتصال یا آزمون واقعی از این پروژه ممکن نیست. بنابراین در این مرحله:

- هیچ اتصال، mock، endpoint ساختگی، کلید یا secret اضافه نشد؛
- هیچ سرویس پولی، تماس، پیامک یا تراکنش واقعی/آزمایشی شروع نشد؛
- هیچ دادهٔ `localStorage` صادر، مهاجرت یا حذف نشد؛
- رابط موجود و حالت محلی بازنویسی نشد؛
- تست واحد، API، staging یا عملی سرویس‌دهنده اجرا نشد.

## ۲. پیش‌نیازهای مشترک برای شروع اجرای واقعی

پیش از اتصال هر provider باید موارد زیر در محیط مورد تأیید مالک فراهم و قابل بررسی باشند:

1. **Backend قابل استقرار:** مخزن/workspace دارای runtime و نسخهٔ پشتیبانی‌شده، روش اجرای محلی و CI، API نسخه‌دار و مسئول نگهداری. endpointها باید از نشست معتبر، tenant، مجوز سروری و validation استفاده کنند.
2. **PostgreSQL واقعی:** محیط مجزای staging و production، نسخه و دسترسی شبکهٔ مستند، کاربرهای کم‌دسترسی، migration نسخه‌دار، تراکنش و idempotency. backup رمزگذاری‌شده و آزمون restore پیش از دادهٔ واقعی لازم است.
3. **Staging واقعی:** دامنه و API origin مشخص با TLS؛ جدا از production، دادهٔ غیرواقعی/مجاز، دسترسی محدود، پایش و امکان rollback. webhook باید از اینترنت/شبکهٔ provider به staging برسد و پس از اعتبارسنجی رد یا پذیرفته شود.
4. **مدیریت secret سمت سرور:** secret manager یا سازوکار محیطی محافظت‌شده با دسترسی حداقلی، جداسازی staging/production، rotation، audit دسترسی و redaction لاگ. secret نباید در کد مرورگر، `localStorage`، repository، log یا گفت‌وگو قرار گیرد.
5. **تصمیم‌های مالک:** انتخاب کشور/میزبان و providerهای مجاز، بودجه و اجازهٔ صریح هر سرویس پولی، حریم خصوصی/رضایت و retention، نقش‌های مجاز، سیاست پشتیبان‌گیری و مسئول تأیید انتشار. هیچ انتخاب یا هزینه‌ای در این مرحله از طرف مالک انجام نشده است.
6. **شواهد provider:** مستندات/API version جاری، مالکیت حساب و پذیرش شرایط، دسترسی sandbox، روش احراز webhook، محدودیت نرخ، منطقهٔ پردازش داده و پشتیبانی از بازار/شبکهٔ هدف. اتصال production جداگانه نیازمند تأیید صریح مالک است.

تا تکمیل این پیش‌نیازها، ساختن adapter یا پیکربندی ظاهری در فرانت‌اند به معنی اتصال نیست و عمداً انجام نمی‌شود.

## ۳. ترتیب اتصال و معیار پذیرش مستقل

هر اتصال باید به‌صورت adapter سروری مستقل، ابتدا در sandbox و سپس در staging انجام شود. feature flag سمت deployment باید امکان خاموش‌کردن provider را بدون حذف داده یا fallback پنهان فراهم کند. خطای server نباید بی‌صدا به دادهٔ محلی تبدیل شود. برای هر مرحله، نسخهٔ کد، تنظیمات غیرمحرمانه، شناسهٔ تست، زمان، نتیجه و محدودیت‌ها ثبت شوند؛ secret و اطلاعات شخصی در گزارش قرار نگیرند.

### ۳.۱ هوش مصنوعی — اولویت نخست

**لازم از مالک:** provider/model و مجوز تجاری، امکان استفاده از محل میزبانی منتخب، شرایط پردازش/عدم‌آموزش و محل داده، سقف هزینه/مصرف، قابلیت‌های فارسی موردنیاز و اجازهٔ استفاده از دادهٔ آزمایشی. Secret دسترسی فقط از secret manager سرور دریافت شود.

**پیاده‌سازی موردنیاز:** درخواست از backend proxy عبور کند؛ کلید هرگز به مرورگر نرسد. اعمال timeout، محدودیت اندازه/نرخ/هزینه، سقف مصرف tenant، قطع‌کنندهٔ مدار، مدیریت پاسخ ناقص/خطا، حذف یا کمینه‌سازی PII، log پالایش‌شده و ثبت model/version لازم است. مدل نباید اختیار مستقیم برای تغییر نقش، ثبت پرداخت، مصرف سهمیه یا اجرای عملیات برگشت‌ناپذیر داشته باشد؛ ابزارها allowlist، مجوز سروری و در صورت لزوم تأیید انسانی می‌خواهند.

**تست مستقل و معیار قبولی:**
- unit: ساخت درخواست، validation، mapping پاسخ/خطا، timeout و محاسبهٔ سقف مصرف؛ داده و کلید در log ظاهر نشوند.
- API در sandbox: پاسخ موفق فارسی، ورودی نامعتبر/بیش‌ازحد، provider timeout/429/5xx، کلید نامعتبر، سقف tenant تمام‌شده و retry کنترل‌شده.
- قبولی: هیچ secret در bundle/شبکهٔ مرورگر دیده نشود؛ خطای provider به پاسخ امن و قابل‌مشاهده تبدیل شود؛ مصرف هم‌زمان از حد مجاز عبور نکند؛ قطع سرویس قابلیت‌های غیرمرتبط را مختل نکند؛ هزینه و latency اندازه‌گیری و در محدودهٔ مصوب مالک باشند.

### ۳.۲ تلفن و ثبت تماس

**لازم از مالک:** provider و قرارداد/شمارهٔ مجاز، حساب sandbox، کشور و مسیر تماس، تأیید مجوز و رضایت ضبط/پردازش، سیاست ذخیرهٔ شماره/صوت/متن، webhook قابل دسترس و کلید/امضای webhook در secret manager.

**پیاده‌سازی موردنیاز:** ایجاد تماس فقط از سرور و با احراز مجوز؛ صحت ورودی webhook (امضا، timestamp و replay window)، deduplication بر اساس شناسهٔ provider، tenant mapping سروری، timeout/retry و ثبت وضعیت تماس در transaction. تماس دستی، رویداد جعلی یا تماس sandbox نباید تماس واقعی معرفی شود. صوت و transcript جدا از metadata، با دسترسی محدود و retention مصوب نگهداری شوند.

**تست مستقل و معیار قبولی:**
- unit/API: webhook امضای نامعتبر، timestamp منقضی، replay، رویداد تکراری، ترتیب رویداد نامنظم و تماس ناشناخته.
- sandbox/staging: تماس ورودی و خروجی مجاز؛ زنگ‌خوردن، پاسخ، عدم پاسخ، خطای provider، قطع تماس و ثبت نهایی در DB. تطبیق شناسهٔ تماس provider با رکورد tenant درست بررسی شود.
- تست تماس واقعی فقط پس از اجازهٔ صریح مالک و ارائه‌دهنده، در شماره/محیط مجاز انجام می‌شود. قبولی: webhook تکراری رکورد/اثر تکراری نسازد؛ tenant دیگر قابل دسترسی نباشد؛ وضعیت‌ها مطابق گزارش provider باشند؛ recording فقط با رضایت و سیاست مصوب فعال شود.

### ۳.۳ پرداخت

**لازم از مالک:** درگاه و حساب پذیرندگی مجاز، قرارداد و شرایط کشور/ارز، دسترسی sandbox، URL callback روی TLS، سیاست refund/لغو، مبلغ/واحد و محصولی که فروش آن تصویب شده است. اعتبارنامهٔ درگاه فقط در secret manager سرور قرار گیرد.

**پیاده‌سازی موردنیاز:** backend از DB سفارش و مبلغ را بخواند و checkout بسازد؛ کلاینت نتواند مبلغ، ارز، مالک سفارش یا وضعیت پرداخت را تعیین کند. callback به‌تنهایی اثبات پرداخت نیست: امضا/شناسه بررسی شود، verify مستقل از API درگاه انجام شود، مبلغ/ارز/سفارش تطبیق یابد و ثبت رویداد + تغییر وضعیت در transaction idempotent باشد. پاسخ مرورگر به صفحهٔ موفقیت مجوز fulfillment نیست.

**تست مستقل و معیار قبولی:**
- sandbox/API: پرداخت موفق، ردشده، لغوشده، callback با مبلغ/ارز نادرست، امضای نامعتبر، callback دیررس، retry، شناسهٔ تراکنش تکراری و verify ناموفق.
- تست صریح پرداخت تکراری: ارسال همان callback چند بار و هم‌زمان؛ تنها یک پرداخت و یک اثر fulfillment ثبت شود.
- قبولی: وضعیت `paid` فقط بعد از verify موفق سمت سرور؛ تطبیق دقیق مبلغ، ارز، سفارش و پذیرنده؛ عدم افشای دادهٔ کارت؛ تمام انتقال‌های وضعیت و ردها audit شوند. تراکنش sandbox هرگز درآمد واقعی گزارش نشود.

### ۳.۴ اشتراک‌ها و entitlement

**لازم از مالک:** تعریف نسخه‌دار پلن، قیمت/دوره/محدودیت، grace period، لغو/تمدید/بازپرداخت و اینکه چه قابلیت‌هایی به هر entitlement وابسته‌اند. پرداخت موفق واقعی یا تصمیم مجاز مالک باید منبع فعال‌سازی باشد.

**پیاده‌سازی موردنیاز:** اشتراک فقط در backend و پس از پرداخت verifyشده یا مسیر مدیریتی مصوب فعال شود؛ entitlement در هر درخواست حساس از DB محاسبه شود. job/درخواست قابل‌تکرار برای انقضا و تمدید، تاریخ UTC، idempotency و audit لازم است. فرانت‌اند نمی‌تواند با تغییر تاریخ/status یا plan دسترسی را فعال کند. تغییر پلن، payment و fulfillment وضعیت‌های مجزا دارند.

**تست مستقل و معیار قبولی:** ایجاد بدون پرداخت، پرداخت نامعتبر، فعال‌سازی مجاز، انقضای دقیق در مرز زمان، تمدید، لغو، refund، retry job و دستکاری body؛ بررسی دسترسی پس از expiry. قبولی: مشتری پس از انقضا entitlement ندارد (جز grace period مصوب) و job تکراری اثر مضاعف ندارد.

### ۳.۵ دمو بازاریاب و سهمیه

**لازم از مالک:** واحد مصرف (مثلاً اقدام/دقیقه/سرنخ)، سهمیه و بازهٔ آن، نحوهٔ تخصیص، مالک سرنخ، رفتار در خطای provider و اجازهٔ اقدام پس از پایان سهمیه.

**پیاده‌سازی موردنیاز:** سهمیه از دفترکل سروری و در یک transaction اتمیک با قفل/قید مناسب کم شود؛ نقش بازاریاب، انتساب سرنخ، tenant و idempotency در سرور بررسی شوند. هیچ مقدار `allowance`, `usage` یا `marketerId` از مرورگر مرجع نباشد. تعریف تراکنش باید روشن کند مصرف در چه نقطه‌ای ثبت می‌شود و در شکست provider چطور بازگردانده/اصلاح می‌شود، همراه audit.

**تست مستقل و معیار قبولی:** سهمیهٔ صفر/یک، تلاش پس از پایان، بازپخش درخواست، تغییر `localStorage`/payload، دسترسی بازاریاب دیگر و درخواست هم‌زمان بیش از سهمیه. قبولی: مصرف کل از سقف عبور نکند؛ عملیات تکراری دوباره مصرف نکند؛ رد مجوز/سهمیه بدون تماس یا هزینهٔ ناخواسته انجام شود.

### ۳.۶ اعلان‌ها

**لازم از مالک:** کانال مورد تأیید (داخل محصول، ایمیل، SMS یا push)، provider و sandbox، رضایت/opt-out، template و زبان، زمان‌بندی/retention و سقف ارسال/هزینه. اعلان محلی فعلی به‌عنوان ارسال خارجی تلقی نشود.

**پیاده‌سازی موردنیاز:** ابتدا رویداد قابل‌اعتماد از backend، سپس صف و adapter؛ recipient از رکورد مجاز سرور تعیین شود. امضای webhook وضعیت تحویل، idempotency، retry/backoff، dead-letter و محدودیت نرخ لازم‌اند. وضعیت «در صف»، «ارسال‌شده» و «تحویل‌شده» جدا باشند؛ شکست provider نباید واقعیت ارسال را جعل کند.

**تست مستقل و معیار قبولی:** opt-out، recipient نامعتبر/خارج از tenant، provider timeout/429/5xx، webhook تکراری و retry. قبولی: گیرنده/متن فقط با مجوز و رضایت ارسال شود؛ retry پیام تکراری نسازد؛ وضعیت تحویل بر اساس تأیید provider باشد. ارسال واقعی فقط با اجازهٔ صریح مالک و تست‌کنندهٔ مجاز.

## ۴. دروازه‌های آزمون staging و انتشار

هیچ سرویس تا گذر از دروازهٔ قبلی به مرحلهٔ بعد نرود:

1. **دروازهٔ زیرساخت:** health check محیط، TLS، جداسازی staging، DB migration/backup/restore، secret isolation و webhook ingress/egress تأیید شوند.
2. **دروازهٔ امنیت پایه:** نشست و CSRF/CORS، tenant isolation با دو tenant، ماتریس چهار نقش، object-level authorization، rate limit و log redaction آزمون شوند؛ کاربر غیرمجاز نباید دادهٔ مالی یا متعلق به tenant دیگر را دریافت/تغییر دهد.
3. **دروازهٔ سرویس مستقل:** برای هر adapter تست‌های unit و API ناموفق/موفق و تست idempotency/retry در sandbox با گزارش شواهد اجرا شوند. شکست یک provider باید به‌طور ایمن fail شود.
4. **دروازهٔ جریان‌های ترکیبی:** پرداخت verifyشده فقط یک بار اشتراک را فعال کند؛ پرداخت نامعتبر/تکراری هیچ entitlement ندهد؛ اشتراک منقضی دسترسی را قطع کند؛ quota هم‌زمان از حد عبور نکند؛ webhook تماس/اعلان تکراری اثر مضاعف نداشته باشد.
5. **دروازهٔ داده و بازیابی:** فقط پس از تصویب مالک و backup قابل بازیابی، migration جداگانه در tenant staging با preview، import version، quarantine، reconciliation و rollback تمرین شود. این مرحله به‌تنهایی مجوز مهاجرت production یا پاک‌کردن localStorage نیست.
6. **دروازهٔ production:** گزارش تست، محدودیت‌های شناخته‌شده، هزینهٔ اندازه‌گیری‌شده، طرح rollback/incident، مانیتورینگ، مسئول on-call، تأیید صریح مالک و اجازهٔ جداگانهٔ هر سرویس پولی ثبت شوند. تا آن زمان پروژه آمادهٔ انتشار یا فروش اعلام نمی‌شود.

### قالب ثبت شواهد آزمون آینده

برای هر اجرا یک رکورد غیرمحرمانه ثبت شود: نام تست و نسخهٔ قرارداد/provider؛ محیط (unit/local/sandbox/staging/production)؛ commit/build ID؛ زمان UTC؛ پیش‌شرط‌ها؛ شناسهٔ مصنوعی/غیرشخصی تست؛ نتیجهٔ مورد انتظار و واقعی؛ log/correlation ID پالایش‌شده؛ هزینه/latency در صورت مجاز؛ اشکال/محدودیت؛ نام نقش تأییدکننده. token، secret، شمارهٔ کامل، متن تماس یا اطلاعات پرداخت در سند/لاگ قرار نگیرد. در وضعیت فعلی هیچ رکورد تست واقعی برای سرویس‌ها وجود ندارد.

## ۵. تصمیم‌ها و دسترسی‌هایی که مالک باید فراهم کند

- تأیید workspace/repository بک‌اند، runtime/version، مسئول توسعه و استقرار، CI و روش rollback.
- ارائهٔ محیط PostgreSQL staging و production، دسترسی کم‌دسترسی، network allowlist/TLS، migration و backup رمزگذاری‌شده همراه نتیجهٔ restore drill.
- تعیین دامنه/API origin، DNS، گواهی TLS، CORS مجاز، دسترسی webhook ورودی و egress؛ برای بازار ایران بررسی واقعی مسیرهای شبکه و محدودیت provider از میزبان منتخب.
- انتخاب هر provider به‌صورت جدا (AI، تلفن، پرداخت، اعلان) و ارائهٔ دسترسی sandbox از مسیر امن secret manager؛ هرگز credential را در chat یا فایل فرانت‌اند ارسال نکنید. production credential و سرویس پولی فقط پس از اجازهٔ صریح مالک.
- تصویب بودجه و سقف هزینه/مصرف؛ بازار/کشور هدف؛ قرارداد و شرایط استفاده؛ مالکیت داده، رضایت، محل پردازش، retention/deletion و پاسخ‌گویی به رخداد.
- تصویب پلن، entitlement، سیاست refund/لغو، quota و واحد مصرف، بسته‌های بازاریابی و معیار fulfillment، و نقش‌های مجاز برای عملیات مالی.
- تأیید مهاجرت جداگانه: tenant مقصد، export/backup قابل‌بازیابی، داده‌های مجاز، اپراتور و کاربر تأییدکننده، preview و معیار rollback. بدون این تأیید import انجام نشود.

## ۶. وضعیت چهار مرحله

| مرحله | وضعیت مستندات/کار انجام‌شده | پیاده‌سازی واقعی | تست واقعی |
|---|---|---|---|
| ۱. آماده‌سازی زیرساخت backend | شواهد workspace و نیازهای محیط در README مستند شده؛ امکان اجرای backend در این workspace اثبات نشده است. | انجام نشده | تست backend/DB اجرا نشده |
| ۲. احراز هویت و امنیت | طراحی جریان و کنترل‌ها در `docs/security-auth-phase2.md` مستند شده است. | انجام نشده؛ auth، session و RBAC سروری وجود ندارد | unit/API/security اجرا نشده |
| ۳. API، DB و مهاجرت | قرارداد، موجودیت‌ها و طرح مهاجرت در `docs/api-data-migration-phase3.md` مستند شده است. | endpoint، schema، migration یا import ساخته/اجرا نشده | تست API/DB/migration اجرا نشده |
| ۴. اتصال سرویس‌ها و آزمون مرحله‌ای | این سند برنامه و معیار پذیرش را مشخص می‌کند. | هیچ provider متصل نشده | sandbox/staging/تلفن/پرداخت اجرا نشده |

این چهار عنوان، چهار مرحلهٔ نقشهٔ راه‌اند؛ مستندشدن هر مرحله به معنای پیاده‌سازی یا قبولی آزمون آن نیست. برای شروع اجرای عملی، ابتدا زیرساخت واقعی و تصمیم‌های مالک در بخش‌های بالا باید فراهم شود، سپس backend/auth/DB و آزمون امنیتی پایه عملی شوند، بعد API دامنه و مهاجرت مجاز، و در نهایت اتصال هر provider در sandbox و staging انجام شود. **هیچ سرویس متصل نشده و پروژه آمادهٔ انتشار یا فروش نیست.**
